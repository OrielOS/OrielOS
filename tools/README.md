# tools

Developer scripts. They are written in Bash (except `build-wiki.mjs`, which is Node), must pass shellcheck, and are meant to run inside Linux or WSL2.

Contains:

- `check-env.sh`: checks that this machine can build and boot-test the image.
- `build-image.sh`: builds the image locally from the pinned inputs and exports an archive for test VMs. It builds and tags the `app-builder` stage first, as `localhost/orielos-app-builder`, so removing old images doesn't throw away the apps' build cache; a rebuild of the same commit with another version then only rebuilds the last layer. Local builds are `dev.1`, `dev.2` and so on; CI passes `--version` with the version it publishes. It keeps only the newest build and its archive (`--keep N` keeps more, as the update test needs the previous build), and stops at once if another build or a VM test is running: they take turns through the lock in `lib/lock.sh`.
- `clean.sh`: frees the space builds and VM tests leave behind, and prints the space used before and after. It removes the VM test folders (disks kept with `--keep` too), the disks from `make-vm-disk.sh`, images loaded from build archives, every build but the newest, stopped containers, the working containers interrupted builds leave (Podman lists them only with `--external`), untagged images and all but the newest five result folders in `tests/results`. Other folders in `/var/lib/orielos` and other local images are listed, not removed. `--all` also removes the newest build and every image no container uses, including the base images and the app builder, which the next build downloads and builds again. It refuses to run while a build or VM test holds the lock, or while QEMU or an image build runs without it. Inside WSL it ends with how to compact WSL's disk file, which keeps its largest size on Windows until it is compacted. Runs as root.
- `build-wiki.mjs`: builds the GitHub wiki from the user documentation in `docs/` with Node 22 and no dependencies: `node tools/build-wiki.mjs --out DIR [--repo OWNER/NAME] [--docs DIR]`. Every top-level `docs/*.md` file becomes a page named after its first heading (`docs/README.md` becomes Home), relative links are rewritten to work on the wiki, and it writes a sidebar and a footer that tells readers to change `docs/` instead. `--out` must be empty or missing; it exits 1 if two files get the same page name or a link points to a missing docs page. `--repo` defaults to `$GITHUB_REPOSITORY`, else `ncjsvr/OrielOS`; `--docs` defaults to `docs`. Its tests are in `tools/test/` and run with `node --test "tools/test/*.test.mjs"`; the Wiki workflow runs them and publishes the result.
- `make-vm-disk.sh`: installs the image to a virtual machine disk, for QEMU (`orielos-<tag>.qcow2`, compressed) and VMware (`orielos-<tag>.vmdk`, a single growable file), and prints their paths and sizes. The tag is the image's version, for example `dev.1` or `v0.0.7`. It installs with `bootc install to-disk` onto a sparse raw file, the same way the boot test does, converts it with `qemu-img` and deletes the raw file. The disks have no user account: Plasma Setup creates the first one on first boot. The defaults are `localhost/orielos:latest`, 64 GiB, both formats and `/var/lib/orielos/vm-disks`; `--archive FILE` installs an archive from `build-image.sh` instead, and removes the image it loaded from it when it's done. `--serial-console` sends the console, systemd's status lines and kernel messages to the first serial port and turns the boot splash off, for debugging and for `vmware-vm.sh boot-check`. Runs as root. See [Try OrielOS in a virtual machine](../docs/install-vm.md).
- `next-version.sh`: prints the version the next published build gets, from the tags already in the registry on standard input: `vMAJOR.MINOR.PATCH`, one more than the highest, with PATCH rolling over after 10 and MINOR after 100 (`v0.0.10` is followed by `v0.1.0`, `v0.100.10` by `v1.0.0`). The Image workflow runs it.
- `build-changelog.sh`: prints what's new in a build, the entries the CHANGELOG's Unreleased section gained since the previous build, from the CHANGELOG at both builds' commits. The Testing release workflow writes each testing build's notes with it.
- `vmware-vm.sh`: creates, boot-checks and deletes a VMware Workstation VM from the VMDK. It runs inside WSL2 on a Windows host with VMware Workstation installed, and drives Workstation's `vmcli.exe` and `vmrun.exe` through Windows interop.
  - `create --vmdk FILE --dir WINDOWS_DIR [--name NAME]` copies the VMDK to `WINDOWS_DIR\NAME` and creates a VM there with UEFI and Secure Boot, 6 GB of memory, 4 CPUs, the disk on an NVMe controller, NAT networking (VMXNET3), an HD Audio sound card, USB 3 and the first serial port writing to `NAME-serial.log` next to the `.vmx` file. VMware runs VMs only from the Windows file system. There is no virtual TPM, because Workstation needs VM encryption for one, which is set up in its window.
  - `boot-check --vmx FILE [--timeout S]` starts the VM without a window, waits up to S seconds (default 600) until the serial log shows `Finished plasma-setup.service` or `Started sddm.service` together with `Reached target graphical.target`, prints PASS or FAIL and stops the VM. It needs a disk made with `--serial-console`.
  - `delete --vmx FILE` stops the VM if it runs and deletes it with `vmrun deleteVM`, together with its serial log and folder.
- `sync-labels.sh`: creates or updates the GitHub labels listed in `.github/labels.yml` with `gh`; `--dry-run` prints the commands and `--prune` removes GitHub's overlapping default labels.
- `update-pins.sh`: shows, and optionally applies, newer digests for the pinned inputs in `image/pins.env`.
- `mirror-pins.sh`: copies every image pinned in `image/pins.env` to `ghcr.io/ncjsvr/mirror` with the same digest, so builds still find it after the upstream registry drops it; `--check` only reports. CI's Mirror workflow runs it. `lib/pins.sh` holds the helpers the build tools use to pull a pin from that copy, or from upstream when there's none.
- `test-apps.sh`: builds and tests OrielOS's own apps the same way the image build does, without building the whole image. It builds only the `app-builder` stage of `image/Containerfile`, which compiles the apps, runs their tests and `qmllint`, and exits 1 if any of them fail. It works with rootless Podman, needs no `sudo`, and CI runs it on every pull request that changes a file the app build reads (the list is in `.github/workflows/apps.yml`).
- `preflight.sh`: runs what CI checks on a pull request, before the branch is pushed: that every image digest and URL in `image/pins.env` is still served (a cached image would otherwise hide one the registry has dropped), that every commit since the base branch is signed off with a Conventional Commit subject, `lint.sh`, and `test-apps.sh` when the branch changes a file the app build reads. It prints PASS, FAIL or SKIP for each and exits 1 on any failure. `--base REF` names the branch the pull request goes into (default `origin/main`), `--apps` and `--skip-apps` force the app build on or off.
- `lint.sh`: runs every linter (shellcheck, shfmt, hadolint, actionlint, clang-format, gitleaks) and exits 1 on any finding. `qmllint` runs in `test-apps.sh` instead, where the Qt and KDE Frameworks imports resolve. Run `tools/install-lint-tools.sh` once first; it installs the pinned tools into `.cache/tools`. The pinned versions and checksums are in `lint-tools.env` and `lint-requirements.txt`. CI runs the same two scripts.
